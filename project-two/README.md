# CS-305 Project Two — Artemis Financial Secure Software

## Overview

For Project Two, I refactored the Artemis Financial Java application to improve secure communications and demonstrate data integrity verification. The main requirements were to implement a SHA-256 checksum and configure the application to communicate over HTTPS instead of HTTP.

## What I Implemented

I modified the existing Spring Boot application to include a new `/hash` endpoint. This endpoint generates a SHA-256 checksum using Java's built-in MessageDigest class and UTF-8 encoding.

I also generated a self-signed certificate using Java Keytool and configured Spring Boot to use HTTPS on port 8443. The certificate and private key were stored in a password-protected PKCS12 keystore.

The keystore password is referenced through an environment variable instead of being hardcoded into the application configuration.

## Security Testing

After refactoring the application, I performed several tests:

- Compiled the updated Java application successfully using Maven.
- Verified the HTTPS endpoint returned HTTP 200.
- Independently calculated the SHA-256 checksum using PowerShell.
- Confirmed the checksum matched the result generated by the Java application.
- Ran OWASP Dependency-Check 13.0.0 to identify known vulnerabilities in the application's dependencies.
- Manually reviewed the application code and configuration for security and functional issues.

## Security Findings

OWASP Dependency-Check scanned 49 dependencies and identified 254 vulnerability findings across 14 vulnerable dependencies.

Many of these findings were associated with outdated libraries, including Spring Boot, Spring Framework, Apache Tomcat, and SnakeYAML.

The new security functionality was successfully tested, but these dependency vulnerabilities remain unresolved. The application would require additional remediation before being suitable for production.

## Running the Application

Use **JDK 11** and **Maven 3.8.1 or newer**, with `java`, `keytool`, and `mvn` on your PATH. The POM retains Java 8 source/target compatibility, but Dependency-Check requires Java 11 or newer. JDK 11 also fits the [compatibility range for Spring Boot 2.2.4.RELEASE](https://docs.spring.io/spring-boot/docs/2.2.4.RELEASE/reference/html/getting-started.html#boot-features-system-requirements). The [Dependency-Check Maven documentation](https://dependency-check.github.io/DependencyCheck/dependency-check-maven/) specifies Maven 3.8.1 as its minimum; an old Maven 3.6.x wrapper will not work for that plugin. No Maven wrapper is included.

The commands below use PowerShell 7 and start in the repository root. Confirm `mvn -version` shows the intended JDK and Maven versions.

### Build and test

```powershell
Set-Location project-two/application
java -version
mvn -version
mvn clean package
```

This compiles the application, runs the Spring context and `/hash` response tests, and creates `target/ssl-server-0.0.1-SNAPSHOT.jar`. The MockMvc tests do not open a network listener and do not prove TLS works. A keystore is required when starting the actual server below.

`package` does not run Dependency-Check, which is bound to the later `verify` phase. A successful package build is not a clean vulnerability scan. Maven may need network access to download dependencies on the first build.

### Generate a local certificate

From `project-two/application`, generate a new development keystore. Choose a new password at Keytool's hidden prompt; do not put it in the command or a tracked file. Use the same password when prompted again in the next step. If a keystore already exists, reuse it only if you know its password, or choose a different filename and update `ARTEMIS_KEYSTORE_PATH` accordingly.

```powershell
keytool -genkeypair -alias artemis -keyalg RSA -keysize 3072 `
  -sigalg SHA256withRSA -validity 365 -storetype PKCS12 `
  -keystore artemis-keystore.p12 `
  -dname "CN=localhost, OU=CS305, O=Artemis Financial, C=US" `
  -ext "SAN=dns:localhost,ip:127.0.0.1"

# Export only the public certificate for the verification client.
keytool -exportcert -rfc -alias artemis -storetype PKCS12 `
  -keystore artemis-keystore.p12 -file artemis-certificate.cer
```

Keep the keystore in the application directory, outside `src/main/resources`. This avoids bundling its private key into the application JAR. Both generated files are ignored by Git. The self-signed certificate is for local testing only.

### Configure and start HTTPS

Set the password only in the current PowerShell process and its child processes. The application requires `ARTEMIS_KEYSTORE_PASSWORD`; it has no hard-coded password or fallback. `ARTEMIS_KEYSTORE_PATH` is optional and defaults to `file:./artemis-keystore.p12`, relative to the working directory.

```powershell
$securePassword = Read-Host 'Local keystore password' -AsSecureString
$env:ARTEMIS_KEYSTORE_PASSWORD = [System.Net.NetworkCredential]::new('', $securePassword).Password
$env:ARTEMIS_KEYSTORE_PATH = 'file:./artemis-keystore.p12'

try {
    java -jar target/ssl-server-0.0.1-SNAPSHOT.jar
} finally {
    Remove-Item Env:ARTEMIS_KEYSTORE_PASSWORD -ErrorAction SilentlyContinue
    Remove-Item Env:ARTEMIS_KEYSTORE_PATH -ErrorAction SilentlyContinue
    $securePassword.Dispose()
}
```

The server binds to `127.0.0.1` and uses HTTPS on port **8443**. Open `https://localhost:8443/hash`. A browser will warn unless it explicitly trusts your development certificate. Stop the server with Ctrl+C. Keep this vulnerable demonstration local.

### Verify the checksum and HTTPS independently

In a second PowerShell 7 window with `curl.exe` available, change to `project-two/application` and run the following. It trusts only the public certificate generated above for this request; it does not disable certificate validation or install a system-wide trusted certificate.

```powershell
$sha256 = [System.Security.Cryptography.SHA256]::Create()
try {
    $data = 'Jonathan Miranda - CS 305 Project Two - Artemis Financial - 2026-10-17'
    $expected = [BitConverter]::ToString(
        $sha256.ComputeHash([Text.Encoding]::UTF8.GetBytes($data))).Replace('-', '').ToLowerInvariant()
    $result = @(curl.exe --silent --show-error --fail-with-body --noproxy '*' `
        --cacert artemis-certificate.cer --resolve localhost:8443:127.0.0.1 `
        --write-out "`n%{http_code}" https://localhost:8443/hash)
    if ($LASTEXITCODE -ne 0) { throw 'HTTPS request failed.' }
    $status = $result[-1]
    $body = $result[0..($result.Count - 2)] -join "`n"
    if ($status -ne '200' -or
        $body -cne "Name: Jonathan Miranda`nData: $data`nSHA-256 Checksum: $expected") {
        throw 'HTTPS or checksum verification failed.'
    }
    "HTTPS status: $status"
    "SHA-256: $expected"
    'Checksum match: True'
} finally {
    $sha256.Dispose()
}
```

The expected checksum is `69e8214bbe1873589b5b3478891e532d87f7cd39980ccbe90df5ea427e281119`. The fixed input has no trailing newline.

### Run a dependency assessment

The POM configures Dependency-Check **13.0.0** to read `NVD_API_KEY` from the environment. If you have an NVD API key, enter it without placing its value in shell history:

```powershell
$secureApiKey = Read-Host 'NVD API key' -AsSecureString
$env:NVD_API_KEY = [System.Net.NetworkCredential]::new('', $secureApiKey).Password
try {
    mvn verify
} finally {
    Remove-Item Env:NVD_API_KEY -ErrorAction SilentlyContinue
    $secureApiKey.Dispose()
}
```

The first scan needs network access and may take a long time to populate the vulnerability database. NVD strongly limits unauthenticated requests, so a key is recommended for practical use. The generated report is `target/dependency-check-report.html` and stays out of Git. Inspect the report even if Maven exits successfully: this POM does not configure a CVSS failure threshold. No suppression rules are used.

The historical report records 49 dependencies scanned (28 unique), 14 vulnerable dependencies, 254 findings, and zero suppressed findings on October 17, 2026. These are reported findings, not proof that all are exploitable. Fresh scan totals can change. The full original HTML report is not included in this repository.

## CI/CD

Four [GitHub Actions workflows](../.github/workflows/) automate build checks and security visibility. No workflow deploys or starts the HTTPS server. They retain Spring Boot 2.2.4.RELEASE and Dependency-Check 13.0.0.

| Workflow / job | Triggers | Results and failure behavior |
| --- | --- | --- |
| [Java CI / Build and Test](../.github/workflows/java-ci.yml) | PRs targeting `main`, pushes to `main`, manual | Runs `mvn clean package` with Temurin Java 11 and the Ubuntu runner's Maven 3.8.1+; compilation or test failures fail the job. Surefire XML/text results are retained for 14 days. |
| [CodeQL / Analyze Java](../.github/workflows/codeql.yml) | PRs targeting `main`, pushes to `main`, Tuesday 06:23 UTC, manual | Uses CodeQL action v4, `java-kotlin`, and a manual `mvn clean compile` build. Publishes Java security findings to code scanning. Requires the setup confirmation below. |
| [Dependency Review / Review Dependency Changes](../.github/workflows/dependency-review.yml) | PRs targeting `main` | Compares dependency changes between the PR base and head. Fails for introduced high/critical known vulnerabilities in runtime, development, or unknown scopes. No advisory exceptions or warning-only mode are configured. |
| [OWASP Dependency-Check / Scan Dependency Baseline](../.github/workflows/dependency-check.yml) | Wednesday 07:41 UTC, manual from `main` | Runs the POM's `dependency-check:check` goal and retains its HTML report for 30 days. A missing key, scan error, or missing report fails the job. |

The workflows copy `project-two/application` to the runner's temporary directory before Maven builds or scans it. Maven dependencies are cached against the POM; PR jobs restore the cache without saving changes. The Ubuntu 24.04 image supplies Maven, and each Maven job logs its version. CodeQL uses a temporary source root that preserves `project-two/application` in finding paths.

Normal Java CI uses `package`, not `verify`, so it does not run Dependency-Check or need `NVD_API_KEY`. The context and `/hash` tests use MockMvc without a network listener. They need no certificate or keystore password and do not verify TLS. CodeQL analyzes the application Java source compiled by Maven using its default security queries; it does not prove HTTPS behavior or replace dependency assessment.

Dependency Review checks newly introduced dependencies. It does not fail an unrelated PR just because the unchanged application has historical findings. Dependency-Check assesses the current baseline, including older vulnerable libraries. The historical **254 findings across 14 vulnerable dependencies** remain unresolved. The POM has no CVSS failure threshold, so a successful Dependency-Check job means the assessment completed and produced a report; it does not mean the report is clean. No vulnerabilities are suppressed to pass these workflows.

### Required GitHub configuration

1. Enable GitHub Actions and allow the pinned official `actions/*` and `github/codeql-action` releases. This public repository is eligible for CodeQL and Dependency Review, but actual Actions policies, dependency-graph availability, and CodeQL default setup could not be verified: the implementation account had read-only access and the relevant APIs returned 403. Branch protection also could not be confirmed. An empty branch-rules response does not establish that all protection is absent.
2. Check **Settings → Advanced Security → CodeQL analysis** before activating advanced analysis. If default setup is enabled, switch to advanced setup and disable default setup first. Then create the repository Actions variable **`CODEQL_ADVANCED_SETUP`** with the value **`true`** under **Settings → Secrets and variables → Actions → Variables**. Until this is confirmed, the advanced job fails before CodeQL initialization and clearly reports that analysis did not run. Keep default and advanced analysis from running together. If retaining default setup, leave the variable unset and remove this advanced workflow before requiring a CodeQL check.
3. Enable the dependency graph under the repository security settings and confirm Dependency Review can read PR dependency changes. Public-repository eligibility alone does not prove it is operational. An API or feature failure must be resolved; the workflow does not turn it into a passing review.
4. Under **Settings → Secrets and variables → Actions → Secrets**, add a repository secret named **`NVD_API_KEY`**. Use a new or rotated NVD key because a previously used key may have been exposed in an old assignment archive. Enter it only into GitHub's secret field; do not put it in source, YAML, command arguments, or logs. No existing key was requested or inspected during implementation.

After the workflow is on `main`, open [Actions](https://github.com/jmiranda89/cs-305-software-security/actions), select **OWASP Dependency-Check**, choose **Run workflow**, and select **main**. Other branches are rejected before the secret is used. Scheduled runs use the default branch and may be delayed by GitHub. The first NVD database update can take time; API limits, network errors, or the 90-minute job limit can prevent completion.

Open the run's **Summary** and job logs for build/test results and Dependency Review findings. Download **java-test-results** for Surefire XML/text output. For Dependency-Check, read the scan summary, logs, and **dependency-check-report** HTML artifact, including reports uploaded after a scan failure when available. CodeQL findings appear under [Security → Code scanning](https://github.com/jmiranda89/cs-305-software-security/security/code-scanning). A successful CodeQL analysis can still publish findings; merge policies for those alerts are configured separately.

Require **Build and Test** and **Review Dependency Changes** in branch protection after their first hosted runs succeed. Require **Analyze Java** once advanced setup and result uploads are verified. The workflows alone do not configure merge protection. PR workflows run for documentation-only changes too, so required checks are not left pending by path filters. Do not make the scheduled Dependency-Check job a PR requirement.

Workflow tokens have `contents: read`; only the CodeQL job also requests `security-events: write`. Checkout does not persist Git credentials. Actions are pinned to verified release commit hashes. PR jobs receive no NVD secret, and no workflow uses `pull_request_target`, creates certificates, disables TLS verification, or uploads application packages or keystores. The report upload paths are restricted to test results and the dependency HTML report.

The [GitHub advanced setup documentation](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/configure-code-scanning/configuring-advanced-setup-for-code-scanning), [Dependency Review action documentation](https://github.com/actions/dependency-review-action), and [Dependency-Check Maven goal documentation](https://dependency-check.github.io/DependencyCheck/dependency-check-maven/check-mojo.html) describe the setup and result behavior. Hosted checks, live CodeQL uploads, Dependency Review operation, and a fresh NVD assessment still need verification with repository access. Passing Java CI does not establish production readiness or resolve the historical dependency risks.

## Portfolio Validation

The original `MessageDigest` implementation and Spring Boot dependency versions are preserved. Portfolio cleanup adds an endpoint response regression test, replaces the leftover configuration placeholder comment, and moves the development keystore outside the classpath. The server is restricted to loopback for local use.

Validation on October 19, 2026 used Eclipse Temurin **11.0.32.1**, Maven **3.9.16**, and PowerShell **7.6.5**:

- `mvn clean package` passed using cached dependencies: **2 tests, 0 failures, 0 errors, 0 skipped**.
- The packaged application returned HTTP **200** over HTTPS on port **8443**, with the exact expected response and SHA-256 checksum.
- The PowerShell verification example above passed against a newly generated local certificate, with certificate validation enabled. The client rejected the certificate when it was not explicitly trusted.
- Plain HTTP did not return a successful response on the HTTPS port. Starting the server without `ARTEMIS_KEYSTORE_PASSWORD` failed as expected.
- The packaged JAR contained no keystore or private-key files. The temporary keystore and certificate were removed after testing.
- A fresh Dependency-Check assessment **did not complete**. Offline execution was rejected by the plugin; a separate credential-free invocation with automatic updates disabled and an isolated data directory stopped with `NoDataException` because that directory had no vulnerability database. Existing NVD credentials and the user's database cache were not reused. Run `mvn verify` with network access and an appropriately configured NVD key to obtain a current report.

These checks do not remediate the unresolved dependency vulnerabilities or establish production readiness.

## What I Learned

This project helped me better understand how encryption, hashing, and secure application configuration work together. I was able to implement HTTPS, generate a certificate, and independently verify that the application produced the correct SHA-256 checksum.

I also learned that adding security features does not automatically resolve vulnerabilities in existing dependencies. Regular testing and dependency maintenance are still necessary to keep an application secure.
